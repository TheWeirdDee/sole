A privacy-preserving exclusivity protocol on STRK20

A right, held by one party, without revealing who.

Sole makes an economic right privately ownable and publicly enforceable. The chain proves the right can be claimed exactly once. It never learns the claimant, the amount, or the relationship behind it.

How it works

Three values. One is shared, two stay private.

01 — identity

slot_key

Poseidon(TAG_SLOT, canonical id). Deterministic, so any party derives the same key and collides. This is what makes a second claim fail.

02 — ownership

claim_record

Poseidon over the slot, a claimant secret, and a shielded funding note. Private. Only the holder can open it.

03 — consumption

nullifier

Burned once at settlement. Producing it needs the claimant secret, so only the holder settles — and never twice.

The public chain holds only slot_key → state → commitment. Never an identity, an amount, or a counterparty.

The privacy boundary, stated plainly

The enforcement state is public. The relationship is private.

A vague privacy claim is worse than none, so here is the whole thing.

DataPublicPrivate
Right state (unclaimed / active / consumed)shown
Slot identifierqueryable*
Claimant identityhidden
Funding amountshielded
Claimant walletanonymizer boundary
Counterparty relationshiphidden

*Anyone holding the canonical id can read a right's state. Sole hides the economic relationship behind that state, not the fact that a known right is active.

Why the privacy layer is causal, not decorative
Without STRK20: Bank A → public wallet → public funding → public relationship With STRK20: Bank A → shielded funding → private transfer → anonymizer → claim() → public ACTIVE state

Remove the anonymizer and the claiming wallet becomes the caller on the public transition — the identity leaks and the thesis collapses. The nullifier that consumes a claim is STRK20's own double-spend primitive, reused rather than reinvented.

Protocol

The state machine and the assumptions under it.

Shipped states

register_right() ( — ) ───────────▶ UNCLAIMED │ claim(commitment) [assert UNCLAIMED] ▼ ACTIVE │ settle(nullifier) [assert ACTIVE, nullifier fresh] ▼ CONSUMED (terminal) forbidden, each asserted and tested: ACTIVE --claim--> REVERT RIGHT_ALREADY_ACTIVE ← the thesis (replay) --settle--> REVERT NULLIFIER_ALREADY_SPENT (wallet) --any--> REVERT CALLER_NOT_ANONYMIZER

The invariant

for every slot_key: state ∈ {UNCLAIMED, ACTIVE, CONSUMED} state = ACTIVE ⇒ exactly one valid claim commitment state = CONSUMED ⇒ no new claim may become ACTIVE and: claimant, amount, counterparty ∉ public registry state

Assumptions we state, not hide

AssumptionStance
A canonical id maps to one real right (no double-minting)MVP: first-registration-wins. Production: attester-signed root.
Anyone with the canonical id can read a right's stateBy design. Low-entropy ids are enumerable; the relationship stays private.
Timing / entry-exit correlation on the shielded legsShield ahead of time; do not shield-then-immediately-claim.
Contracts are ownerless and unauditedA finding means a redeploy, not a patch. Adversarial coverage is not an audit.

Roadmap, documented not shipped

ACTIVE → EXPIRED (deadline), ACTIVE → CANCELLED (holder aborts), ACTIVE → PARTIALLY_SETTLED → CONSUMED. Interface and spec only. Three clean states on mainnet beat six half-working ones.
